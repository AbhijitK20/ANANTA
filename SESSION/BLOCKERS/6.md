# Session 6 blockers

Independent validation and the named relaxation ladder.

## 2026-09-26 objectiveFast and objectiveNaive disagree on 7 of 10 components
- blocked on: `lib/engine/scoring/components.ts` (session 4) vs
  `lib/engine/validation/components-naive.ts` (me)
- symptom: `lib/engine/validation/drift.test.ts` describe "the credibility
  anchor", 4 tests red. On the 12-record synthetic fixture a four stop plan
  reports `drift 7.588e+0` against a tolerance of `1e-6`. The per-component
  table, which is doing its job, names them in this order:
  `travelFriction` (3.60), `interest` (2.90), `value` (1.38), `weather` (1.29),
  `authenticity` (0.87), `novelty` (0.72), `crowd` (0.25), `rating` (1.21 on
  some windows), `groupFit`, `reliability`.
- why i cannot fix it: `scoring/` is session 4's, and more importantly this is
  not a bug in either file. Section 3 of `SESSION/00-CONTRACTS.md` names the ten
  components and four aggregate terms but gives a closed form for only five of
  them (`superlinearTravel`, `crowdLoad`, `redundancyPenalty`, `paceDeviation`,
  `proximityDecay`). Two people reading the same ten names wrote two different
  models. Picking mine would be the validator marking its own homework, which is
  the exact failure this session exists to prevent.
- proposed one-line fix: session 1 (or 1 and 4 jointly) appends the closed form
  of each component to `lib/engine/objective-spec.md`, then both
  implementations conform. My proposals, per component, with the reasoning:

  1. **travelFriction is the big one.** The spec's per-stop utility includes
     `w.proximity * proximityDecay(stops[i], ctx)` and its aggregate includes
     `W.travelPenalty * superlinearTravel`. Session 4 has no proximity term at
     all and defines `travelFriction` per stop as `-(travelMinutes /
     availableMinutes)`, i.e. a share of the window. Mine keeps proximity in the
     utility and the quadratic in the aggregate, which is the literal reading.
     *Proposal: keep both. Add a `proximity` weight to `Weights`, use it for
     `proximityDecay`, and keep the quadratic solely in the aggregate. Note that
     `Weights` has no `proximity` key today, so the spec's own `U_i` references
     a weight the type does not declare.*
  2. **interest.** Spec silent. Mine is `interests[category] - avoid[category]`.
     Session 4 divides by the profile total, which is scale free. *Proposal:
     session 4's, because a traveller who lists six interests and a traveller who
     lists one should not be scored on different scales.*
  3. **value.** Spec says only "0 when price is unknown". Session 4 returns 0
     unless `record.confidence.price` is `verified` or `community`, which is the
     masterplan rule that a hash-derived price must not buy ranking. Mine ignores
     provenance. *Proposal: session 4's, and it is strictly better. I will
     conform.*
  4. **weather when unknown.** Spec says "0 when weather is unknown". Session 4
     returns 0.5. *Proposal: 0, as written. Unknown is not a mild positive, and
     the masterplan is explicit that unknown is not `false` either, so it
     should not be a quiet +0.5 either.*
  5. **crowd and novelty: per stop or aggregate?** The spec puts `crowdLoad` and
     `redundancyPenalty` in the *aggregate* penalty list. Session 4 computes both
     per stop, so the panel shows a per stop crowd and novelty score that the
     scalar never actually uses in that form. *Proposal: aggregate, as written.
     This is the second structural divergence and it changes the breakdown, not
     just a constant.*
  6. **peakHourFactor interpolation.** Spec pins 1.0 at the best time and 0.4 at
     the opposite end and leaves the middle open. Both implementations chose
     1.0 / 0.7 / 0.4 on a 4-ring, and they agree, which is a good sign the ring
     reading is the intended one. No action needed.
  7. **rating.** Both read `wilsonLowerBound(ratingSum, reviewCount * 5)`. These
     now agree to 1e-6. See the bug I found below, which I fixed on my side.

- severity: blocker

## 2026-09-26 Wilson bound needed a five star trial count, and I had it wrong
- blocked on: nothing, fixed on my side, recorded because it is a live trap
- symptom: `objectiveNaive` returned NaN for every record with reviews.
  `wilsonLowerBound(46, 10)` puts the proportion at 4.6, `p * (1 - p)` goes
  negative, and `Math.sqrt` returns NaN. The whole scalar became NaN and
  `compareDrift` reported `drift NaN`, which `NaN <= 1e-6` evaluates to false,
  so it failed loudly. It would not have failed loudly if the clamp had come
  first.
- why i could not fix it in one place: `ExperienceV2.ratingSum` is a sum of
  stars, so the trial count is `reviewCount * 5`, but the frozen signature in
  section 4 is `wilsonLowerBound(positive, total)` and the field is named
  `ratingSum`, not `positiveCount`. The name invites the wrong call.
- proposed one-line fix: in `contracts/types.ts`, rename the doc on
  `ratingSum` to state that it is a sum of stars on a five point scale and that
  the Wilson trial count is `reviewCount * 5`. I have added that note to
  `wilsonLowerBound` in `components-naive.ts` and I have clamped the
  proportion to [0, 1] so the mistake degrades to a wrong number rather than a
  NaN. Session 4 already does both.
- severity: cosmetic (fixed, but the type doc should say it)

## 2026-09-26 Weights has no proximity key but the objective's U_i uses one
- blocked on: `lib/engine/contracts/types.ts:240` (session 1)
- symptom: section 3 writes `U_i = ... + w.proximity * proximityDecay(...)`,
  but the `Weights` interface declares only interest, rating, value,
  authenticity, weather, crowd, novelty, groupFit, travelFriction, reliability,
  travelPenalty and pacePenalty. There is no `proximity` weight to read, and
  `ComponentId` has no `proximity` member either, so the per stop proximity
  term has no home in the breakdown.
- why i cannot fix it: `contracts/` is session 1's and section 2 is frozen. A
  design gap in the frozen types is reported, not patched.
- proposed one-line fix: add `proximity: number;` to `Weights` and
  `"proximity"` to `ComponentId`, or state in the spec that `proximityDecay` is
  folded into `travelFriction`. Meanwhile `components-naive.ts` reads
  `(weights as { proximity?: number }).proximity` and falls back to an exported
  `PROXIMITY_WEIGHT_FALLBACK = 0.15`, so the day the key exists both
  implementations use their own number with no edit here. One deleted line
  removes the fallback.
- severity: blocker

## 2026-09-26 ScoreComponent.contribution cannot be weight * normalised at plan level
- blocked on: `lib/engine/contracts/types.ts:250` (session 1)
- symptom: the type says `contribution` is `weight * normalised`, and
  `normalised` is documented as living in [-1, 1]. A plan is a sum over stops,
  not an average, so a plan of four stops with interest 0.5 contributes 2.0
  while `weight * normalised` is 0.5. My first attempt used per stop means for
  the contribution and the panel did not reconcile with the score: the rows
  summed to -29.43 against a score of -29.51 on a two stop plan.
- why i cannot fix it: frozen type.
- proposed one-line fix: amend the comment to say `contribution` is the plan
  total for the component and `normalised` is the per stop average, so
  `contribution = weight * normalised * stopCount` at plan level. Also note that
  `normalised` cannot be held inside [-1, 1] for an unbounded quadratic
  distance penalty, and should not be squashed to fake it.
- severity: degraded

## 2026-09-26 Four ValidationIssue codes have no home in the codes table
- blocked on: `lib/engine/contracts/codes.ts` (session 1)
- symptom: `ValidationIssue.code` is `RejectionCode | "objective_drift" |
  "window_overflow" | "budget_overflow" | "empty_plan"`. The last four are not
  `RejectionCode`s, so `REJECTION_CODES` has no sentence builder for them and

- why i cannot fix it: `codes.ts` is session 1's, and adding four codes to
  `RejectionCode` would widen a frozen union that sessions 3, 8 and 10 already
  iterate.
- proposed one-line fix: session 1 adds a `VALIDATION_ISSUE_CODES` table beside
  `REJECTION_CODES` in `codes.ts`, keyed by the four validation-only codes, and
  I will switch the six codes in my files that *are* `RejectionCode`s over to
  `REJECTION_CODES[code].sentence(...)`. Until then
  `lib/engine/validation/window.ts` documents that the sentences are local.
  There is also no code for a plan that is short of `ctx.minStops`: it is a
  count rather than a measured shortfall, so `validate` reports it through
  `satisfiedFraction` and through `hardChecks().name` instead of inventing a
  code under which it would say something else. A `too_few_stops` code would be
  the honest fix.
- severity: degraded

## 2026-09-26 sold-out comparison is only exact when both timestamps carry the same offset
- blocked on: `lib/engine/contracts/types.ts:153` (session 1)
- symptom: `checkConditions` compares `Date.parse(ctx.now) +
  arrivalOffset * 60000` against `Date.parse(record.availability.soldOutAt)`.
  JavaScript reads an offset-less timestamp as host local time, so a `ctx.now` of
  `2026-01-01T09:00:00` and a `soldOutAt` of `2026-01-01T09:30:00Z` are compared
  in different timezones and the check is wrong by the host offset. It happened to
  be right on this machine and wrong by 5.5 hours elsewhere, which is worse than
  being consistently wrong.
- why i cannot fix it properly: converting through `ctx.city.timezone` needs a
  timezone database, and the dependency list is frozen. Deriving a fixed offset
  per city would itself be a fabricated fact, which the masterplan forbids.
- proposed one-line fix: state in the `DiscoveryContext.now` doc comment that it
  must carry the same UTC offset form as `Availability.soldOutAt`, and add
  `utcOffsetMinutes: number` to `CityManifest` so callers can normalise both
  sides. I have left the check exact-but-fragile and documented the ceiling in
  `window.ts` rather than papering over it.
- severity: degraded

## 2026-09-26 greedy_fill takes an injected pool instead of importing pack()
- blocked on: nothing, a deliberate design choice, recorded for the record
- symptom: the frozen signature is `relax(stops, ctx, cause)`, which carries no
  candidate list, so a refill step has nothing to draw from. I added an optional
  fourth argument `options.pool`, which keeps the three argument signature
  intact and type-checks against it.
- why: two reasons, both in the comment at the top of `ladder.ts`. A static
  import of `packing/` takes every test in this directory down with it while
  session 5 is mid flight, and a validator that builds its own fixups through
  the packer cannot tell whether the packer or the check is wrong. Session 7's
  `solve` already holds a packed plan and can pass its shortlist in for free.
- proposed one-line fix: none. If session 1 prefers, the pool can be threaded
  through `PackResult` instead, but the optional argument is the smaller change
  and the one that keeps the frozen signature.
- severity: cosmetic
