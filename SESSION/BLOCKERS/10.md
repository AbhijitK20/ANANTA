## 2026-09-26T00:05:00Z objectiveFast and objectiveNaive disagree on five components, and the naive derivation is the correct one on at least three

- blocked on: `lib/engine/scoring/objective-fast.ts` and `lib/engine/validation/components-naive.ts`
- symptom: measured objective drift of `2.498` on `one-of-us-wants-solo` and `4.876e-1` on `elderly-step-free`, against a tolerance of `1e-6`. `describeDrift` names the rows. The per-component comparison for a single-stop plan on `tight-budget`, with the weight column shown, is:

  | component | fast normalised | fast weight | naive normalised | naive weight |
  |---|---|---|---|---|
  | `interest` | 0 | 1 | 0 | 1 |
  | `value` | 1 | 0.6 | 1 | 0.6 |
  | `authenticity` | 0.9 | 0.7 | 0.9 | 0.7 |
  | `weather` | **0.5** | 0.5 | **0** | 0.5 |
  | `crowd` | **-0.3** | 0.6 | **+0.3** | 0.6 |
  | `novelty` | 1 | 0.45 | 0.9428 | 0.45 |
  | `groupFit` | 0 | 0.8 | **0.25** | 0.8 |
  | `travelFriction` | -0.004762 | **0.7** | +0.0760 | **0.004** |
  | `reliability` | 0.5 | 0.25 | 0.5 | 0.25 |

- why i cannot fix it: `lib/engine/scoring/**` is session 4 and `lib/engine/validation/**` is session 6. Both are on my FORBIDDEN list.
- proposed one-line fix: three separate corrections, one per row.

  1. `weather`: `MASTERPLAN.md` section 3.2 and `SESSION/00-CONTRACTS.md` section 3 both say `weatherFit(r, ctx) // 0 when weather is unknown`. `ctx.weatherSeverity` is `null` in this scenario, so the naive value of 0 is the specified one and `objectiveFast` should return 0 for an unknown severity, not the 0.5 neutral.
  2. `travelFriction`: the objective's aggregate term is `- W.travelPenalty * superlinearTravel(...)`, and `PRIOR_WEIGHTS.travelPenalty` is `0.004`. The fast path is charging the per-stop utility weight `travelFriction` (0.7) instead, which is a different coefficient applied to a different term. Either drop `travelFriction` from the per-stop utility and let the aggregate penalty carry it, or give it its own weight key in `Weights`.
  3. `crowd`: the fast path's normalised value is `-0.3` where the naive is `+0.3`, and the naive's own contribution is `-0.18` despite the positive normalised value, so at least one of the two applies the sign twice or not at all. `crowdLoad` is a penalty term in the objective, not a utility component, so it should be subtracted once and only once.

## 2026-09-26T00:05:00Z an empty openingHours.weekly is treated as "closed", which is not what "unverified" means

- blocked on: `lib/engine/feasibility/checks/hours.ts:49-53`
- symptom: 1,072 of 1,090 records in `anantaRecords` carry `openingHours.confidence === "unverified"` with an empty `weekly` map. The check emits `closed_now`, which is **blocking**, so every one of them is refused. The eval suite reports coverage of 45.5% and mean time utilisation of 17.6% because of it, against targets of 90% and 85%. `closed_now` is the single most frequent rejection code in 22 of 22 scenarios, at roughly 130 of 140 candidates each time.
- why i cannot fix it: `lib/engine/feasibility/**` is session 3.
- proposed one-line fix: at `hours.ts:49`, branch on the confidence before branching on the schedule, so that an unverified schedule is refused for the reason it is actually unverified:

  ```ts
  if (openingHours.confidence === "unverified") {
    rejections.push(reject("hours_unverified", {}, cause));
    return rejections;
  }
  ```

  `SESSION/00-CONTRACTS.md` already sets `hours_unverified` as `advisory: true` in `contracts/codes.ts`, and `contracts/types.ts:59` already says an empty map means "not known, which is NOT the same as always open". The comment at `hours.ts:43-44` says the intent, but the code only honours it when `weekly` happens to be non-empty. The one-line change makes the data model and the check agree.

  Note the consequence: with this change these records pass the gate carrying an **advisory** rejection, so the UI must render the advisory. `components/ananta/why-not-that.tsx` and the feasibility meter are session 9's, and they need to show a non-blocking "opening hours unverified" chip rather than treating an advisory as a refusal.

## 2026-09-26T00:05:00Z publishing a submission does not yet reach Explore

- blocked on: `app/explore/page.tsx` and `components/ananta/use-ananta.ts`
- symptom: `applyPublishedListings(records, listings, now)` in `lib/provider.ts` is the function that makes a published submission discoverable, and `lib/provider.test.ts` proves it adds a submitted id to the catalogue and overrides an existing record's price, duration and availability. But the catalogue the engine reads is `anantaRecords` from `lib/data/ananta/records`, which is a module-level constant built at import time, so nothing merges the published overlay into it. The loop is closed up to the last line.
- why i cannot fix it: `lib/data/**` is session 8 and `app/explore/**` is session 9. A module-level `const` cannot be extended from outside without an accessor, and adding one is session 8's change.
- proposed fix, two lines across two owners.

  Session 8, in `lib/data/ananta/records.ts`, export an accessor that applies an overlay:

  ```ts

    listings: readonly { id: string; status: string; availability: string; updatedAt: string; priceInr: number | null; durationMinutes: number | null }[],
  ): ExperienceV2[] {
    return applyPublishedListings(anantaRecords, listings as ProviderListing[], "1970-01-01");

  ```

  importing `applyPublishedListings` from `@/lib/provider`. That is a dependency from `lib/data` to `lib/provider`, which inverts the intended layering, so the cleaner shape is for `applyPublishedListings` to move to `lib/data/ananta/overlay.ts` and for `lib/provider.ts` to re-export it.
