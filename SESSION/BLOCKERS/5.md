## 2026-09-26T23:45:00+05:30 buildStops has no way to resolve an id to a record
- blocked on: `lib/engine/packing/pack.ts:60` (the frozen signature, `SESSION/00-CONTRACTS.md` section 4)
- symptom: `export function buildStops(order: string[], ctx: DiscoveryContext, options: PackOptions): Stop[]` takes ids, but neither `ctx` nor `options` carries a `ExperienceV2`, and `Stop.record` requires one. A three-argument call of the shape the barrel is wired to either throws `buildStops: no record supplied for id "..."` or returns `[]`, which is a silently empty plan.
- why i cannot fix it: `PackOptions` and `buildStops` are session 5's, but the signature is frozen in the contract and session 1 owns `lib/engine/index.ts`, which is where the export is wired. A module-level record registry would be exactly the module-level mutable state the purity rules forbid, so that is not an option.
- proposed one-line fix: `buildStops(order: string[], ctx: DiscoveryContext, options: PackOptions, records: ExperienceV2[]): Stop[]` as a required fourth parameter, with `pack` passing the table it already builds. If a fourth parameter is unwelcome, keep the signature and add `records: ExperienceV2[]` to `PackOptions`, which is what I did, and which is structurally compatible with the frozen interface either way.
- severity: degraded

Cost of the workaround: `buildStops` is not callable by a caller that only has ids. `pack` populates the table internally so the product path is unaffected, but session 7's replan and session 10's eval both build stops directly and will need to pass the same table. A required fourth parameter makes that impossible to forget; an optional field makes it possible to get wrong at runtime rather than at compile time. I would rather have the compile error.

## 2026-09-26T23:45:00+05:30 Mercator projection inflates distances by about 5.9 percent at this latitude
- blocked on: `lib/engine/contracts/manifest.ts:17` (the bbox latitudes)
- symptom: `buildDistanceMatrix` projects to Web-Mercator metres, which is conformal and not equidistant, so a projected separation at 19 degrees north is about 1 / cos(19) = 1.0585 times the great-circle distance. The clustering radius and the cluster diameter bound are calibrated against the projected numbers, so a cluster holds about 5.5 percent fewer kilometres than the radius suggests.
- why i cannot fix it: the projection is what the contract asked for in `SESSION/05-PROMPT.md` item 1, and `lib/engine/validation/distance-naive.ts` belongs to session 6, which re-derives distances with its own haversine.
- proposed one-line fix: none required. The two notions are deliberately separate and each is used only for what it measures: projected metres decide what counts as a cluster, the injected route matrix decides what a leg costs, and `Stop.travelKm` comes only from the injected matrix, which is what keeps session 6's independent re-derivation able to agree to 1e-6. `distance.test.ts` asserts the 1.05 to 1.07 ratio out loud so a future reader does not have to rediscover it. Flagging it because a 5.9 percent error in a radius is the kind of thing that gets mistaken for a data bug later.
- severity: cosmetic

## 2026-09-26T23:45:00+05:30 LAHC finds nothing to improve once the construction is already a local optimum
- blocked on: `lib/engine/packing/pack.ts` step 7, my own file
- symptom: `searchStats.acceptedImprovements` is 0 on most instances, and the final objective is identical across seeds. The beam already optimises the real objective, and 2-opt plus Or-opt then run to a local optimum of the same neighbourhood LAHC samples, so the search has nothing left.
- why i cannot fix it: this is not a defect, it is a property of the pipeline at 2 to 4 stops, and the number is load bearing: it is the debug view's answer to "did the search do anything". Making it non-zero by counting sideways acceptances would be a lie in a field named `acceptedImprovements`.
- proposed one-line fix: none. Two things were fixed along the way and both are real improvements, so noting them for whoever tunes the weights: the penalty step is now calibrated per instance from the local objective spread rather than fixed at 0.5, because a fixed step an order of magnitude larger than the objective deltas blinded the search entirely; and the penalty now charges accepted solutions only, not every candidate that was proposed. A tight 16 candidate grid with `idealStops: 4` reports 3 to 5 accepted improvements across six seeds, and the default three-quarter fixture reports 0. Both are asserted, including the zero, because a zero there is a true statement about the search.
- severity: cosmetic
