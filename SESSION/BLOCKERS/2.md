## 2026-09-26T23:41:00Z retrieve has no city manifest in its frozen signature, and the isochrone needs one
- blocked on: SESSION/00-CONTRACTS.md section 4, `export function retrieve(index: SearchIndex, options: RetrieveOptions): RetrieveResult;`
- symptom: `RetrieveOptions` has no manifest and `buildIndex(records)` has no manifest, but the isochrone prefilter is specified as the thing that takes 1107 candidates down to about 120, and the contract for it says "Uses `city.congestion`, never a raw radius". There is no way to reach a `CityManifest` from either frozen argument.
- why i cannot fix it: `RetrieveOptions` is frozen in section 4 and is not mine to widen.
- proposed one-line fix: no change needed to `RetrieveOptions`. I carry the manifest on `SearchIndex` as `manifest: CityManifest | null`, which is legal because `SearchIndex` is undefined in the contract. The UI should call `buildCityIndex(records, getCityManifest(id))`, or `withManifest(buildIndex(records), manifest)`; the bare frozen `buildIndex(records)` yields `manifest: null` and `retrieve` then skips the prefilter rather than inventing a congestion multiplier. Please confirm this is the intended shape when you uncomment the barrel.
- severity: degraded (worked around by putting the manifest on the index; cost is that a manifest-less index silently has no travel filter)

## 2026-09-26T23:42:00Z RetrieveOptions has no travel mode, so the prefilter has to assume one
- blocked on: SESSION/00-CONTRACTS.md section 4, `export interface RetrieveOptions`
- symptom: the isochrone needs a `TravelMode` to pick a speed and a congestion multiplier. `RetrieveOptions` carries none, and `DiscoveryContext.travelMode` is not reachable from `retrieve`.
- why i cannot fix it: `RetrieveOptions` is frozen and not mine to widen.
- proposed one-line fix: add `travelMode?: TravelMode` to `RetrieveOptions`, defaulting to `"walk"`. I have already exported `DEFAULT_TRAVEL_MODE` from `lib/engine/retrieve/retrieve.ts` and documented it, so the change is one optional field plus reading it in place of the constant. Walk is a safe interim because it is the only mode whose estimate cannot overstate reachability, and the filter is allowed to remove records.
- severity: degraded (a caller with a 60 minute taxi budget currently gets a 60 minute walk filter, which is far too tight)

## 2026-09-26T23:43:00Z CityManifest has no field for a mode's straight-line speed
- blocked on: lib/engine/contracts/types.ts, `export interface CityManifest`
- symptom: `isochrone.ts` needs a km/h figure per travel mode. `CityManifest.congestion` is a multiplier with no base to multiply, so the speeds had to live in the engine.
- why i cannot fix it: `CityManifest` is frozen and owned by session 1.
- proposed one-line fix: add `speeds: Record<TravelMode, number>` to `CityManifest` and move `MODE_SPEED_KMH` out of `lib/engine/retrieve/isochrone.ts` into the manifests. The values I use are in `MODE_SPEED_KMH` and are generic mode physics, not city data, so nothing in the engine is city-specific today. The upgrade path is measured per-mode speeds, which belong in the manifest, not the code.
- severity: cosmetic

## 2026-09-26T23:45:00Z The ten Devanagari rows are in the geocode match field, not in ExperienceV2
- blocked on: lib/data/geocoded.generated.ts, the `match` field of 10 rows
- symptom: my brief said about ten rows whose `match` is Devanagari. That is true: 10 rows, 8 unique strings, all in `geocoded.generated.ts` and none elsewhere. But `match` is only used to choose coordinates during generation, so no `ExperienceV2` field carries Devanagari today. Verified against the live `anantaRecords`: a query for the `devanagari` class token returns 0 of 1090 records.
- why i cannot fix it: `lib/data/**` is owned by session 8, and adding a Devanagari `name` to a record is a data decision, not an engine one.
- proposed one-line fix: nothing required. `foldForMatch` already collapses a Devanagari run to the single token `devanagari` and `tokenize` indexes it, so the moment a record carries a Devanagari name it becomes findable by class and the anomaly is countable rather than invisible. If session 8 wants the ten rows genuinely searchable by name, the fix is a transliteration column, which needs a mapping table nobody has.
- severity: cosmetic
